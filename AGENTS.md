## Efficient execution
- Prioritize reducing agent work units: repeated discovery, test-list/command reconstruction, output naming and evidence extraction. Runtime speed is secondary; fewer internal function calls alone do not mean fewer agent tasks. Automate deterministic steps in existing tools while preserving semantic decisions, authorization and verification coverage.
- For remaining-rule selection, batching, stopping and evidence reuse, apply `WORK_SELECTION.md`. Read it when selecting or revising a batch, not repeatedly during the same batch. This operational standard supersedes older blanket all-source-enumeration and per-clause full-lifecycle repetition wording in checkpoints.
- Resume from the current checkpoint and relevant entry files. Retrieve source/code just in time; do not reread the whole verification corpus every batch. For a code/fixture packet from known navigation targets or file:symbol references, use `work/reuse-partials/assemble_context_packet.py prepare` instead of hand-transcribing a selection spec; its samples do not select mandatory tests.
- For validation from an existing packet/report, test reference or exact navigation target, use `work/reuse-partials/verify_overlay_tests.py --auto TARGET` (default mode 15; mode 13 collects only). It restores current full declarations, records evidence and returns the next action; resolve reported gaps instead of rebuilding lists/commands. Declared scope is not proof of complete change impact or clause acceptance.
- Batch clauses sharing a concrete implementation and verification path. If a group is blocked, record the dependency and work on another independently actionable group.
- Define the behavioral outcome, relevant files, constraints and acceptance checks. Avoid long prescriptive microsteps that duplicate what the implementation owner can infer.
- Use one implementation owner for coupled runtime changes. Delegate only when authorized and when file ownership or read-only responsibilities are independent.
- Do not turn Luna -> Sol -> Astra into a mandatory conveyor for every edit. Subject to the user's current model instructions, use bounded repetitive work for lighter models, integrated changes for capable implementers, and focused review where correctness risk warrants it.
- Pass a compact handoff with source references, changed files, known failures and checks already run. Review must find defects and edge cases, not repeat all prior exploration.
- Prefer existing patterns and shallow composition. Add abstractions for demonstrated shared behavior or the actual scripting requirement; do not build speculative frameworks.
- Run relevant checks after edits. Expand or repeat checks for new changes, failures or unresolved impact; preserve valid prior evidence. Run certification checks against stable code, not concurrently changing shared runtime files.
- Test observable behavior and important boundaries. Avoid tests mirroring implementation and duplicate reporting/publishing scripts for tiny batches.
- Reuse deterministic scripts for inventories and bookkeeping. Keep provenance/audit work out of hot runtime paths unless required by behavior.
- Measure batch wall time, investigation/implementation/verification overhead, repairs and completed behavior. Token counts are not billing amounts. Do not promise a speedup without comparable measurements.
- At every completed work item or batch, check actual waiting and rework across investigation, implementation, verification and acceptance. Repair the confirmed avoidable bottleneck in its existing owner, verify the change, and leave one compact result in the existing batch record before moving on. If no avoidable bottleneck is established or the repair needs new authority, record that fact and the exact next action; do not invent a speedup or silently expand scope. This is a targeted completion check, not a mandatory full-project profile, new ledger or repeat of valid tests.
- Report each completed batch with clause delta, verified total/percentage, checks and any material bottleneck. No model or reviewer guarantees zero bugs.
- Use a known-working tool path after a reproducible tool failure; do not repeatedly retry unchanged failing commands. Permission requirements still apply.

- Root alone merges shared candidates, accepts evidence, updates the existing ledger and reports totals. Agents return isolated payloads, exact evidence references and checks; their local counts are not the chat's completion totals.

Candidate IDs plus canonical published IDs must equal the stated accepted total; accepted stages, classification labels and saved counts must agree. A contradictory checkpoint is not a trusted baseline: report reconciliation pending, retain the conflicting values and exact missing/different IDs, and never invent IDs or silently rewrite history to make the totals match.

Keep original approval evidence; a regression hold must name the exact newly failing required test or independently demonstrated remaining defect. A later PASS still needs the existing source and physical-evidence acceptance gates.
- Persist the report command, exact evidence pointers and unfinished work in the existing continuation checkpoint for handoff/compaction. Do not maintain a second completion ledger, reconstruct totals from chat memory, or silently change the meaning of a reported column.
